# 发布签名与「换钥匙」迁移

本文只讲一件事：仓库历史里那把 APK 签名私钥已经泄露，怎么把它换掉，
以及已经装了旧包的用户怎么迁移。背景与代码修复见
`docs/fixes-v3.4.0-20261104/report-2.md` 的 RR-12。

## 1. 事实与影响面

| 事实 | 依据 |
|---|---|
| 旧私钥 `apk-mod/a2a-mod.jks` 曾被 git 跟踪，口令写在 README 里 | `git show 23b881d:apk-mod/a2a-mod.jks` 可完整取回（2722 字节，PKCS12） |
| 旧证书 SHA-256 | `B1:8B:0E:B2:07:83:29:A9:96:33:22:E8:7F:47:66:99:43:65:5D:B8:57:AA:06:C0:76:DD:86:83:65:C0:BF:15` |
| 旧 keystore 文件 SHA-256 | `25cb9dbd9ddae971347f1499bee97bf6bd8f2c64380d973179dac4cb774a472d` |
| 别名 | `a2a`（`keytool` 用旧口令可列出 `PrivateKeyEntry`） |

影响不是「以后别再用它签名」这么轻：

- Android 判断一个 APK 是不是合法升级，只看**包名 + 签名证书**。持有旧私钥的人
  可以签出同包名、同证书的 APK，已装旧版的手机在系统看来就是一次正常更新，
  **不会弹签名不一致**，用户也看不出区别。
- 这个仓库通过 Magisk 模块分发服务端，APK 一直是用户自己 `adb install` /
  点安装包装的，没有自动更新通道，所以攻击面是「诱导安装一次替换包」，
  不是静默远程升级 —— 但一旦装进去，它拿到的权限就是应用本身的权限
  （本机环回网关地址、面板登录态）。
- 因此：**旧钥匙必须吊销，且已安装用户必须主动换成新签名的包。**

## 2. 换钥匙（一次性，5 分钟）

在仓库外生成，别写进项目目录（脚本会拒绝写进仓库）：

```bash
sh apk-mod/sign-tool.sh new --out ~/.a2a-signing
# 输出里会打印新的证书 SHA-256，记到发布记录里
```

产物：

- `~/.a2a-signing/a2a-release.jks`（PKCS12，RSA 4096，10000 天）
- `~/.a2a-signing/a2a-release.pass`（32 位随机口令，权限 600）

把这两个文件**离线备份两份**。Android 的签名私钥丢了就永远无法给已安装用户
发升级包，只能再走一次「卸载重装」。

想用 HSK/硬件密钥或已有企业证书也行，只要满足：

```bash
sh apk-mod/sign-tool.sh fingerprint --keystore <你的.jks> --alias <别名>
```

输出的指纹不能等于上面那个泄露值（脚本会直接返回 2 并拒绝）。

## 3. 发一次「换签名」版本

Android 不允许跨签名覆盖安装，所以这次升级必然是一次**卸载重装**。建议节奏：

1. **先发说明**：在模块 README / 发布页写清楚「本版 APK 换了签名，需要卸载旧版
   再装；卸载会清掉 App 内的本地设置（服务器地址、面板登录凭据缓存）」。
2. **导出可保留的东西**：手机端只把「服务器地址 / 端口」和面板登录态存在
   WebView 的 localStorage 里，重装后在「服务器」页点「自动发现」或手填一次即可；
   没有需要迁移的业务数据。
3. **发新包**：用新钥匙签名（`apksigner sign`，见 `README-mod.md` 第 5 节），
   在发布说明里附上新证书指纹，方便用户核对。
4. **旧包下架**：把用旧钥匙签过的 APK 从 release / 网盘 / 群里撤掉，避免有人
   拿旧包做「升级」诱导。

用户侧：

```bash
adb uninstall com.agent2api.mobile     # 必须先卸，否则 INSTALL_FAILED_UPDATE_INCOMPATIBLE
adb install -r Agent2API-<ver>-mod.apk
```

> 如果某台手机不方便卸载（例如没有 adb、只在手机上操作），就在系统设置里
> 「应用 → Agent2API → 卸载」，再从文件管理器点新 APK 安装。

## 4. 发布检查清单（每次发 APK 都过一遍）

- [ ] `sh apk-mod/sign-tool.sh fingerprint --keystore "$A2A_KEYSTORE"` 输出**不是**
      `B18B0EB2…C0BF15`（泄露指纹）；
- [ ] `git status` 里没有任何 `*.jks` / `*.keystore` / `*.pass`；
- [ ] 签名口令只从环境变量或密钥管理服务读，CI 日志里搜不到；
- [ ] `apksigner verify --print-certs` 打出的证书 SHA-256 与发布说明里的一致；
- [ ] 发布说明里写了本次证书指纹（换钥匙那次要额外写「需卸载重装」）。

## 5. 为什么不「改写 git 历史」

改写历史（`git filter-repo` / BFG）能让后来 clone 的人看不到私钥，但**不能
让已经泄露的私钥变回秘密**：镜像、fork、别人的本地副本、CI 缓存都可能有。
正确顺序是「先换钥匙、再考虑清历史」，且清历史会改写所有提交哈希、打断已有的
patch/工单引用，属于仓库所有者的决策，不在本次修复范围内。若确实要清，建议
换钥匙发版完成之后再单独做一次，并在 README 里保留一句「历史曾泄露，已吊销」。
